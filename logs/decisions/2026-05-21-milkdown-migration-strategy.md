# Note 编辑器 Milkdown 迁移策略

- 日期：2026-05-21
- 状态：已采纳

## 背景

当前笔记模块已经具备结构化块模型和论文来源联动能力，但编辑器基础行为主要由自研 Renderer 逻辑承担，维护成本较高。随着以下需求持续增长，现有方案风险上升：

- 长文笔记编辑稳定性
- 富文本与 Markdown 并存
- AI 回答和 PDF 摘录的结构化插入
- 图片、截图、表格、公式等复杂块扩展
- 后续插件化编辑器能力

前期评估后，Milkdown 适合作为新的编辑器内核候选，但它不能直接替换当前整套笔记系统。

## 决策

采用“保留现有数据模型、双轨迁移、运行时可回滚”的迁移策略接入 Milkdown。

具体约束如下：

1. 保留 `NoteDocument / NoteBlock / SourceRef` 作为当前稳定数据模型
2. Milkdown 在稳定前仅作为 Renderer 内部编辑内核，不改主进程持久化结构
3. 旧版编辑器与新版编辑器并存，通过实验开关切换
4. 先迁移基础文本块，再迁移 `pdf_excerpt`、`ai_answer`、媒体块等业务块
5. 任一阶段若出现数据映射不稳定、来源信息丢失或复杂块回归，优先切回旧版

## 取舍原因

### 采用该方案的原因

- 能先获得成熟编辑器基础能力，降低选区、撤销、粘贴、输入法等底层维护成本
- 不会一次性打穿现有 Note、PDF、AI、导出和持久化链路
- 对现有数据结构侵入最小，回滚成本低
- 更适合当前“论文来源联动强于通用 Markdown 编辑”的产品形态

### 不采用一次性替换的原因

- 当前 `NoteBlock[]`、`sourceRefs`、图片裁剪/环绕、MinerU 拖入都与业务深度耦合
- 直接整块替换会放大数据丢失、来源失效和导出失效风险
- Milkdown 本身不原生理解当前业务块语义，必须先做适配层

## 影响范围

- `packages/notes`
- `apps/desktop/src/renderer/components/note`
- `apps/desktop/src/renderer/App.tsx`
- 笔记编辑相关导出、复制、来源跳转装配层

3. 为 `NoteDocument <-> Milkdown 文档状态` 建立转换器
4. 在新版稳定前保留旧版编辑器为默认入口
